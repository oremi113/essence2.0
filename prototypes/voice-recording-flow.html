Design system reference

Every primitive the flow above depends on. Open this HTML in 6 months and the complete system rebuilds from this section alone.

BreathStone — all 11 engine states

Each canvas runs the real engine (ported 1:1 from breathStoneEngine.ts). Same Perlin-driven silhouette, same asymmetric breath physics, same per-state lerp targets.

Record button — all 4 states

idle → recording → uploading → saved. The `--finished` green state is the calm post-success rest; `--uploading` holds at 60% opacity during commit.

Pass 2 — required before code

Pass 1 covered the happy path. These six state-coverage gaps are where users break, not where they succeed — add them in Pass 2 before Session 5 lifts any of this into React. Each is a screen (or screen-variant) this prototype does not yet render.

  1. Mic permission denied. Screen 3 has no state for when the user taps "Not now." Flow dead-ends silently. Needs: recovery screen with OS-agnostic instruction + "Open settings" / "Try again" CTAs.
  2. Upload failed / network drop. Recording succeeds, upload fails, no view exists for it. --color-status-error and record-label--error are defined but never surface in the flow. Needs: prompt-screen variant showing error label + retry CTA, preserving the user's recording locally.
  3. Mid-recording OS interrupt. Paused screen is scoped to user-initiated pause. Phone call / backgrounded app is a different UX with a clearer recovery path. Needs: "We paused for you — your last moment is safe" with a single "Tap to resume" primary.
  4. Resume-training entry (returning user). Screen 1 (Entry) assumes a brand-new user. Returning users mid-journey need concrete progress framing, not "Begin voice training." Paused screen semantically mismatches — it's labelled "Paused," not "Resume." Needs: entry variant with "12 of 25 moments complete · Stage 2 next" + populated stage map + "Continue Stage 2" primary.
  5. Mic hardware failure. Distinct from permission denied. Permission granted, but no mic detected or audio levels flatline. No recovery path in the flow. Needs: diagnostic screen "We can't hear you" with "Test microphone" retry + "Skip for now" link.
  6. Re-record / edit flow. The "You can re-record anytime" hint implies an entry point the prototype does not render. From where? List view? In-flow scrubber? Post-training review? Needs a design call in Pass 2 before building. Three candidate directions: (a) "Your recordings" list view, (b) collapsed scrubber above the active prompt, (c) one-at-a-time review during a post-training listen-back.

Decisions pending (Pass 2 — celebration-group round)

  1. Celebration screens ignore the onCelebrateEnd callback. Screens 8 and 11 use data-state="celebrate". The engine emits onCelebrateEnd after the 2200ms gesture and the stone auto-returns to idle — the prototype wires none of this. User has to tap Continue while the gesture is playing or sit afterward waiting. Pass 2 decision: (A) keep tap-to-continue (slower, more reverent; risk of momentum loss), or (B) use the callback — Continue stays dim/disabled for 2200ms, then fades in when the gesture completes (celebration is honored, momentum preserved). Recommended split: B for S1→S2 (early, momentum matters), A for S2→S3 (deeper emotional beat, let them dwell).

Do not ship React without these screens + decisions resolved in this prototype first.
