Design system reference

Every primitive the flow above depends on. Open this HTML in 6 months and the complete system rebuilds from this section alone.

BreathStone — all 11 engine states

Each canvas runs the real engine (ported 1:1 from breathStoneEngine.ts). Same Perlin-driven silhouette, same asymmetric breath physics, same per-state lerp targets.

Record button — all 4 states

idle → recording → uploading → saved. The `--finished` green state is the calm post-success rest; `--uploading` holds at 60% opacity during commit.

Pass 2 — required before code

Pass 1 covered the happy path. These state-coverage gaps are where users break, not where they succeed — add them in Pass 2 before Session 5 lifts any of this into React. Each is a screen (or screen-variant) this prototype does not yet render. Original item numbers preserved so commit history stays referenceable; resolved items moved to the section below.

  1. Mic permission denied. Screen 3 has no state for when the user taps "Not now." Flow dead-ends silently. Needs: recovery screen with OS-agnostic instruction + "Open settings" / "Try again" CTAs.
  2. Upload failed / network drop. Recording succeeds, upload fails, no view exists for it. --color-status-error and record-label--error are defined but never surface in the flow. Needs: prompt-screen variant showing error label + retry CTA, preserving the user's recording locally.
  3. Resume-keepsake entry (returning user). Screen 1 (Entry) assumes a brand-new user. Returning users mid-journey need concrete progress framing, not "Begin voice keepsake." Paused screen semantically mismatches — it's labelled "Paused," not "Resume." Needs: entry variant with "12 of 25 moments complete · Stage 2 next" + populated stage map + "Continue Stage 2" primary.
  4. Mic hardware failure. Distinct from permission denied. Permission granted, but no mic detected or audio levels flatline. No recovery path in the flow. Needs: diagnostic screen "We can't hear you" with "Test microphone" retry + "Skip for now" link.
  5. Working-screen timeout escape. Screen 14 is intentionally no-exit during normal processing — the user is waiting for voice commit and leaving mid-commit strands them. But if processing exceeds ~60s (server hiccup, slow upload, long queue), the user has no recourse and the screen reads as frozen. Flagged in Pass 1 Finding 6. Needs: after ~60s on Working, surface a soft "This is taking a while — check back in a few minutes" action. Dismisses to home; server continues processing and notifies (push/email) when voice is ready. Out of prototype scope; Session 5 call.

Resolved in Pass 2

  1. Celebration screens ignore the onCelebrateEnd callback. Original gap: Screens 7 and 10 (celebrate state) left Continue live from frame 1 while the 2200ms shimmer-and-specks gesture played. Ceremonial moment and "move on" affordance competed for attention — by celebration #2 the ritual was already dead. Resolved 2026-04-17 — both celebrations use option B (callback-gated Continue). The A/B split proposed in the handoff was rejected: teaching two different rules for the same screen shape erodes premium feel. The dwell-longer intuition for S2→S3 is real but belongs in tempo, not in interaction model. Prototype: Continue ships as .btn-primary.is-waiting[disabled], flips to .is-ready after a 2200ms timer aligned with the celebrate one-shot. React port: subscribe to BreathStone.onCelebrateEnd — no timer — and flip isWaiting → isReady on the callback. Replay/navigation resets the state so the second playthrough starts hidden again.

Resolved in Pass 1

  1. Mid-recording OS interrupt. Original gap: Paused screen was scoped to user-initiated pause. Phone call / backgrounded app is a different UX with a clearer recovery path. Resolved 2026-04-17 — landed as the system-interrupt variant of the Paused screen. Title "We paused for you." / subtitle "Your last moment is safe." The two-CTA pattern (Resume primary, Return home secondary) matches the other Paused variants, so the structural sibling relationship is preserved. The in-flow trigger (actual OS interrupt detection) is a production-app concern, not a prototype one.
  2. Re-record flow. Original gap: "You can re-record anytime" hint implied an entry point the prototype did not render. Three directions were considered: list view, inline scrubber, post-keepsake review. Resolved 2026-04-17 — landed as the prompt-screen post-save state. After recording capture, the Saved confirmation transitions into a Re-record + Continue button pair that replaces the record-button cluster in place. The "You can re-record anytime" hint line is removed from all three prompt screens. See ESSENCE_Record_PostSave_State_Spec.md.

Do not ship React without these screens + decisions resolved in this prototype first.
