## What changed

Step 9 ships the Settings & Trust screen (`/app/settings`). It carries five
controls that a churn/retention analysis will want to see. This PR wires the
**server-side** ones through the existing structured logger (`logEvent` /
`logError`), and leaves the **client** ones as a documented gap rather than
firing events an allowlist would silently drop.

### Firing in this PR (server logs, via `logEvent`/`logError`)

Emitted from the Settings server actions / API routes. These are operational
log lines (not `usage_events` yet), keyed by `event`, `requestId`, `userId`:

| Event | Where | Meaning |
|---|---|---|
| `settings.cancel_subscription` | `POST /api/stripe/cancel-subscription` | Confirmed cancel — `cancel_at_period_end` set on Stripe. The retention-loss signal. |
| `settings.email_change_requested` | `changeEmailAction` | Magic-link identity change requested (confirm link sent; not yet confirmed). |
| `settings.remove_photo` | `removePhotoAction` | Home photo removed. |
| `settings.delete_account_complete` | `deleteAccountAction` | Teardown finished successfully. A per-step `settings.delete_account.*` error (via `logError`) with no matching `_complete` is the partial-failure signal — the "delete couldn't finish" terminal. (No `_invoked` start-marker: `LogOutcome` has no `pending`, so a start event would falsely log `success` before any work ran.) |

The actual `active → cancelled` and `active → lapsed` transitions still arrive
via the Stripe webhook (`customer.subscription.updated|deleted`), unchanged.
`settings.cancel_subscription` is the *intent* marker that precedes the
period-end `deleted`.

### Specced but NOT firing yet (the known-gap)

- **`settings.notification_toggled`** (props: `key` ∈ `trial_reminders |
  payment_notices`, `next` bool). The two notification switches are **optimistic
  in the screen only** — `onToggleNotification` is a deliberate no-op in
  `SettingsPageClient` (the same pattern as Home B's dead-linked affordances).
  Two things are missing before it can fire as a real `usage_events` row:
  1. a **notification-prefs store** so the toggle persists (today it reverts on
     reload — FOLLOW_UPS #68); and
  2. an **`/api/analytics` allowlist entry** for the `settings.*` namespace (the
     `track()` transport drops unlisted event names, per
     `docs/analytics/2026-06-16-journey-funnel-events.md`).
- **`settings.card_update_started`** — the "Update" control routes OUT to
  Stripe's hosted portal; the return is observable via the
  `?card_updated=1` param but is not yet a tracked event.

## Root cause

Intentional scoping. The screen is the deliverable; wiring persistence + a new
analytics allowlist entry for notification prefs is out of the Step 9 build
scope and gated behind a store that doesn't exist yet. Firing to an endpoint
that would drop the event is worse than not firing — so the toggle is an honest
no-op with the event pre-specced here.

## When

Landed on the Step 9 Settings branch, 2026-07-06.

## What to watch

- Do **not** expect `settings.notification_toggled` in `usage_events` yet — its
  absence is the known-gap above, not a tracking regression.
- For churn analysis, `settings.cancel_subscription` (log) is the earliest
  in-app cancel-intent marker; the billing-state truth still lands via the
  Stripe webhook writes to `subscriptions`.
- A `settings.delete_account.*` error event (`.stripe_cancel` / `.storage` /
  `.<table>` / `.auth_user`) **without** a matching
  `settings.delete_account_complete` = a teardown that half-failed (user saw the
  "your account is still here" terminal). Watch this for delete reliability.
